O enunciado do OI56 mudou, e isso é metade do trabalho

Ele foi registrado como "o template mira-studio-demo não tem nenhum marcador @MIRA:". A investigação de hoje desmentiu dois dos três sintomas e mostrou que o defeito não é de template nem é dos formatos Studio:

  • @MIRA:RESPONSIVE nunca foi contrato de template. ensureResponsive() o insere quando falta, e nenhum dos 8 templates o traz.
  • Os slots @MIRA:FAST:* são da Fase 1, que os abre mecanicamente sem problema.
  • O que sobra é o @MIRA:THEME — e virou bug próprio, o VPUH.

O bug foi reescrito com o escopo real, por decisão sua. ID e pasta inalterados. Ver o bug.md

2. A decisão de produto que você tomou

Pôr o marcador @MIRA:THEME nos Studio não é cosmético: o CLI substitui aquele bloco por mira-dark.css + base.css, e o base.css traz .anim-stage { height: clamp(400px,60vh,620px) } e body { background: var(--mira-bg) }, que brigam com o Studio (.anim-stage { flex: 1 1 auto } e as barras cinzas #333333). O mira-default só sobrevive porque neutraliza isso no próprio CSS.

Escolhido: declarar os Studio theme-agnósticos. Envolvo o :root que eles já têm nos marcadores e os acrescento à exceção que o sandeco-just-animation-template já tem. Nenhum CSS novo entra em deck nenhum, então o risco visual é zero, e eu não teria como verificar o contrário: não há navegador neste ambiente.

Mantém o comportamento de hoje, só que honesto. Tornar os Studio temáveis de verdade continua possível depois, como feature, com verificação visual.
