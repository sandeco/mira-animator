1. O defeito

Dois bugs, uma pergunta mal respondida em quatro lugares: existe um elemento section aqui? Cada ponto responde aplicando uma regex sobre o texto bruto do arquivo. Texto bruto inclui comentário HTML, comentário JavaScript e o conteúdo de <script> e <style>. Uma frase de documentação que mencione a tag vale tanto quanto a tag.

Manifestação nova, encontrada no diagnóstico

Procurando todos os pontos com o mesmo padrão, achei um terceiro em validate-run.mjs:131-133 que nenhum dos dois bugs descrevia. Um comentário HTML dentro do bloco de HTML do fragmento desbalanceia a contagem do próprio fragmento:

Não abri bug novo: o critério de aceite 3 do BNO4 já exige que validate-run e assemble-run usem o mesmo critério num único ponto. Entra nesta correção e fica registrado na Resolution.

2. Causa raiz

confirmed  Não existe, em lugar nenhum do pipeline, uma função que separe marcação de prosa. Cada ponto reimplementou a mesma pergunta com a mesma resposta errada.

Caminho causal

  1. Um comentário legítimo cita <section> ao explicar a estrutura.
  2. O trecho analisado (esqueleto, saída final ou fragmento) contém esse texto.
  3. /<section\b/i casa com o texto do comentário.
  4. A checagem conclui que existe um elemento onde há apenas uma frase.
  5. Erro: esqueleto reprovado, contagem inflada, ou fragmento dado como desbalanceado.

Evidências

  • Cápsula de reprodução: 3/3 nos dois casos, determinístico, com caso de controle que monta com sucesso trocando <section> por secoes no mesmo comentário.
  • reproduce.mjs: harness hermético, exit 0 hoje, exit 1 depois da correção.
  • codigo-observado.md: os quatro pontos com arquivo e linha, e as 12 menções documentais do template que servem de gatilho.

Descoberta de escopo

A cápsula reproduz no formato mira-vertical, não nos Studio. De propósito: o defeito não é dos templates Studio, é do validador e da contagem, que valem para os quatro formatos. O relato original sugeria um problema do mira-studio; ele é do pipeline inteiro.

3. Estratégia

Correção direta. Não há hipóteses concorrentes a debater: a causa raiz foi reproduzida e o caso de controle isola a variável. O que existe é uma decisão de projeto pequena, que já resolvo aqui: em vez de consertar quatro regexes, crio uma função que responde a pergunta, e os quatro pontos passam a chamá-la. Sem isso, o quinto ponto nasce com o mesmo defeito, como já aconteceu duas vezes.

A função

export function stripNonMarkup(value) {
  return value
    .replace(/<!--[\s\S]*?-->/g, '')                                // comentário HTML
    .replace(/(<script\b[^>]*>)[\s\S]*?(<\/script>)/gi, '$1$2')  // conteúdo de script
    .replace(/(<style\b[^>]*>)[\s\S]*?(<\/style>)/gi, '$1$2');   // conteúdo de style
}

export function countSections(value) {
  return (stripNonMarkup(value).match(/<section\b/gi) ?? []).length;
}

export function countClosingSections(value) {
  return (stripNonMarkup(value).match(/<\/section>/gi) ?? []).length;
}

Mora em validate-run.mjs, que o assemble-run.mjs já importa. Nenhum arquivo novo, nenhuma mudança no que o instalador copia.

Cuidado que o fix precisa respeitar

A remoção de comentários vale só dentro da contagem, nunca na variável compartilhada. Se htmlBlock fosse limpo de comentários antes das outras checagens, a verificação de <!-- @MIRA:SIZE 3/10 --> (validate-run.mjs:138) passaria a falhar sempre, e os marcadores de envelope @MIRA:FAST sumiriam. Aplicar localizado, em cada ponto de contagem.
